## Codebase Patterns
- Handler pattern: extract params → validate UUID → open DB → get run → validate state → update DB → emit event → return response
- `update_pipeline_run()` takes string status values (e.g., "running", "completed") not enum variants — use the string literals directly
- Event bus is `Option<SharedEventBus>` — always check with `if let Some(bus) = &state.event_bus`
- Pre-existing warnings exist in clippy/build — don't try to fix them unless they're in your changed code
- Pipeline question DB functions: insert_question(), get_pending_questions(pipeline_run_id), answer_question(id, answer, answered_by) — answer_question returns bool
- `get_pending_questions()` filters `answered = 0` in SQL, so returns only unanswered questions
- The daemon lock test (`test_acquire_lock_contention`) is flaky when daemon is running — pre-existing issue
- `HandlerState` has `pipeline_signals: PipelineSignals` field — must be initialized with `Arc::new(Mutex::new(HashMap::new()))` in all constructors/tests
- For async signaling between handlers and executor tasks, use `tokio::sync::watch` channels keyed by pipeline_run_id in the shared `pipeline_signals` map
- When updating test files that construct `HandlerState`, all 5 test modules (protocol, e2e, commands_exec, commands_plan, commands_project_spec) must be updated
- Auto-answerer uses `extract_pipeline_json_from_text()` (same as stage output parsing) to extract JSON from Claude's response
- `RunConfig::for_pipeline_auto_answer` limits to Read/Glob/Grep with max_turns=10 — no write/edit/bash access
- `auto_answer_question()` in handlers.rs is the full-flow function: spawn agent → parse → save to DB → emit event
- `extract_pipeline_questions()` parses the PIPELINE_QUESTIONS marker + ```json block from Plan agent output; returns (questions, cleaned_text)
- `run_pipeline_stage()` returns a 3-tuple: `(StageOutput, Option<String>, String)` — the third element is raw result_text for question detection
- For Plan stages, `run_pipeline_stage` strips PIPELINE_QUESTIONS from text before parsing plan JSON to avoid picking up questions as plan output
- Question routing: Auto mode spawns parallel auto-answerer tasks (tokio::spawn), Manual mode polls DB every 500ms until all questions answered
- TUI ring buffers: pipeline_output_buffer is on App (not detail state) — survives detail state recreation when opening pipeline detail views
- `pipeline_stage_icon()` in ui.rs returns dynamic spinner for running stages via `spinner_char()`, static icons for other states
- TUI overlays: Overlay enum in app.rs, rendered by render_overlay() dispatch in ui.rs, key handling goes through handle_key_event's exclusive handler chain
- Pipeline question overlay: PipelineQuestionOverlayState in app.rs, questions stored in pipeline_pending_questions on App, overlay opened/closed via helper methods
- Borrow checker tip: when modifying overlay state and app state in same handler, extract data into locals first (immutable borrow), then modify (mutable borrows)
- Daemon events arrive via two paths: (1) event bus subscription (handle_daemon_event), (2) streaming response data (poll_pipeline_streaming_data) — both must handle new event types
- Pipeline question badge in list view: `pending_question_count_for_run()` helper counts per-run pending questions, shown as "[N ?]" in status column
- Pipeline approval overlay: `PipelineApprovalOverlayState` in app.rs, `ApprovalKind` enum (Plan/Final), opened via `open_pipeline_approval_overlay()`, keybinds 'a' approve/'r' reject
- Approval overlay has two modes: view mode (a/r/j/k/Esc) and rejection mode (text input with Enter/Esc) — controlled by `rejecting` bool field
- Pipeline status strings for approval gates: "waiting_for_approval" and "waiting_for_final_approval" — used in status bar indicator and detail view
- `PipelineNewState` has 3 fields (name, goal, mode) — focused_field cycles 0→1→2 with Tab, mode toggles with Left/Right arrows
- `PipelineRunItem` has `mode: String` field — populated from daemon JSON response, displayed as "M"/"A" badge in pipeline list
- CLI pipeline commands: `PipelineCommand` subcommand enum in cli.rs, streaming for `start`, non-streaming for list/status/cancel/log
- `pipeline.start` is a streaming command — handled in `run()` function before `build_command()`; uses `handle_pipeline_stream()` in streaming.rs
- `pipeline.list`/`pipeline.status` daemon responses now include `mode` field in run JSON — both handlers updated in handlers.rs
- Pipeline formatting: `format_pipeline_event()` for streaming, `print_pipeline_list/status/logs()` for response rendering in format.rs
- Socket timeout: pipeline commands use `LONG_COMMAND_TIMEOUT` (300s) since pipeline.start can run for extended periods
- Interactive CLI mode: `handle_pipeline_stream()` detects manual mode + tty stdin, intercepts `pipeline_question` and `waiting_for_approval`/`waiting_for_final_approval` events for interactive prompts
- For sending commands during streaming, open a separate `SocketClient::connect()` — the main client is occupied by the streaming reader
- `stdin_is_tty()` via `libc::isatty(libc::STDIN_FILENO)` for non-interactive fallback detection

## 2026-02-11 - US-019
- Implemented interactive CLI mode for manual pipeline with stdin questions
- Updated `handle_pipeline_stream()` in streaming.rs to support interactive mode:
  - Detects manual mode from params + checks stdin is a tty via `stdin_is_tty()` (libc::isatty)
  - Tracks `pipeline_run_id` from streaming events for use in interactive commands
  - Intercepts `pipeline_question` events: prints question + context, prompts user for answer via `read_user_input_with_prompt()`, sends `pipeline.answer` command via separate socket connection
  - Intercepts `waiting_for_approval` and `waiting_for_final_approval` events: prints plan/summary, prompts "Approve? (y/n/feedback):", handles y=approve, n=prompt-for-feedback-then-reject, other-text=reject-with-that-as-feedback
  - Non-interactive fallback: if stdin is not a tty, skips all interactive prompts and treats as auto mode (just prints events)
- Added `stdin_is_tty()` function using `libc::isatty(libc::STDIN_FILENO)`
- Added `read_user_input_with_prompt()` function: same as `read_user_input()` but accepts custom prompt string
- For sending commands during streaming (answer/approve/reject), opens separate `SocketClient::connect()` since the main client is occupied by the streaming reader
- Files changed: crates/nflow-cli/src/streaming.rs, scripts/ralph/prd.json, scripts/ralph/progress.txt
- All 101 nflow-cli tests pass, all 801 non-daemon tests pass
- `cargo build --workspace` succeeds, `cargo clippy --workspace --all-targets` passes (no new warnings)
- **Learnings for future iterations:**
  - Cannot reuse the main `SocketClient` during streaming — it's borrowed by `StreamingReader`. Use a separate connection for interactive commands.
  - `libc::isatty()` is already available via the `libc` crate in nflow-cli dependencies
  - Event `type` field values for interactive events: `pipeline_question`, `waiting_for_approval`, `waiting_for_final_approval` — these match what the daemon emits in streaming responses
- `PipelineStageChange` and `PipelineCompleted` events include `mode: String` field — clients can use this for mode-aware routing
  - `read_user_input_with_prompt()` is generic enough for reuse in future interactive CLI features
