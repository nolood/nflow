# nflow — Data Model

## Overview

All persistent state is stored in a single SQLite database at `~/.nflow/nflow.db`. Markdown spec files live on the filesystem and are referenced by path from the database.

## Schema

### projects

```sql
CREATE TABLE projects (
    id          TEXT PRIMARY KEY,          -- UUID
    name        TEXT NOT NULL UNIQUE,      -- human-readable name, set at `nflow init`
    path        TEXT NOT NULL UNIQUE,      -- absolute path to project repo
    base_branch TEXT NOT NULL DEFAULT 'main', -- branch to create worktrees from
    git_provider TEXT NOT NULL DEFAULT 'github', -- 'github' or 'gitlab'
    execution_enabled INTEGER NOT NULL DEFAULT 0, -- 0/1, set to 1 by `nflow run`
    created_at  TEXT NOT NULL,             -- ISO 8601
    updated_at  TEXT NOT NULL              -- ISO 8601
);
```

A project is bound to a directory. `nflow init` in `/home/user/myapp` creates a project with `path=/home/user/myapp`. The `name` is explicitly set by the user.

### specs

```sql
CREATE TABLE specs (
    id              TEXT PRIMARY KEY,      -- UUID
    project_id      TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    name            TEXT NOT NULL,          -- e.g. "auth-login"
    file_path       TEXT NOT NULL,          -- relative to ~/.nflow/projects/{name}/specs/
    status          TEXT NOT NULL DEFAULT 'draft',
    -- Statuses: draft -> approved -> decomposed (or deleted at any point)
    --   draft:       being written, spec session in progress or paused
    --   approved:    user approved the spec, ready for decomposition
    --   decomposed:  plan generated from this spec
    --   deleted:     soft-deleted by user (record hidden, file preserved on disk)
    claude_session_id TEXT,                -- claude session ID for resuming spec session
    session_active  INTEGER NOT NULL DEFAULT 0, -- 1 if a claude process is currently running for this spec
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

CREATE INDEX idx_specs_project ON specs(project_id);
CREATE INDEX idx_specs_status ON specs(status);
```

### work_items

Unified table for epics, stories, and tasks. Hierarchy is expressed via `parent_id`.

```sql
CREATE TABLE work_items (
    id              TEXT PRIMARY KEY,      -- UUID
    project_id      TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    decomposition_session_id TEXT NOT NULL REFERENCES decomposition_sessions(id) ON DELETE CASCADE,
    parent_id       TEXT REFERENCES work_items(id) ON DELETE CASCADE,
    type            TEXT NOT NULL,          -- 'epic', 'story', 'task'
    kind            TEXT NOT NULL DEFAULT 'impl',
    -- Kind (only meaningful for tasks):
    --   impl:   implementation task — writes code, creates a commit
    --   verify: verification task — runs build + tests, checks acceptance criteria
    --            auto-generated by nflow after each impl task
    short_id        TEXT,                  -- display ID from decomposition (E1, S1, T1)
    title           TEXT NOT NULL,
    description     TEXT NOT NULL,          -- detailed description for agent
    acceptance_criteria TEXT,               -- measurable criteria for "done" (markdown list)
    status          TEXT NOT NULL DEFAULT 'pending',
    -- Statuses:
    --   pending:     not yet ready (dependencies not met)
    --   ready:       all dependencies met, can be scheduled
    --   in_progress: agent is working on it
    --   done:        completed successfully
    --   failed:      agent failed, needs user attention
    --   cancelled:   user cancelled
    sort_order      INTEGER NOT NULL DEFAULT 0, -- ordering within parent
    claude_session_id TEXT,                -- agent's claude session ID
    worktree_path   TEXT,                  -- abs path to git worktree (story-level)
    branch_name     TEXT,                  -- git branch name (story-level)
    mr_url          TEXT,                  -- merge request URL (story-level)
    commit_hash     TEXT,                  -- git commit hash (impl tasks only, set on completion)
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

CREATE INDEX idx_work_items_project ON work_items(project_id);
CREATE INDEX idx_work_items_parent ON work_items(parent_id);
CREATE INDEX idx_work_items_type ON work_items(type);
CREATE INDEX idx_work_items_status ON work_items(status);
```

**Hierarchy rules:**
- Epic: `parent_id IS NULL`, `type = 'epic'`
- Story: `parent_id` references an epic, `type = 'story'`
- Task: `parent_id` references a story, `type = 'task'`

**Worktree/branch/MR** are set on **story** level only. Tasks within a story share the worktree.

**Task kinds:**
- `impl` tasks: created by Claude during decomposition. Write code, create commits.
- `verify` tasks: auto-generated by nflow after each `impl` task. Run build, run tests, check acceptance criteria. Do NOT create commits.

**Verify task auto-generation:**
When nflow stores work items from decomposition, it inserts a verify task after each impl task:
```
T1 (impl: Create login endpoint)      sort_order=0
T1v (verify: Verify login endpoint)   sort_order=1
T2 (impl: Add password hashing)       sort_order=2
T2v (verify: Verify password hashing)  sort_order=3
```

The verify task inherits `acceptance_criteria` from its preceding impl task. Its `description` is auto-generated from the template (see prompts.md).

**Pairing:** An impl task and its verify task are paired by `sort_order` adjacency — impl at `sort_order=N`, verify at `sort_order=N+1`. When nflow needs to find the paired verify task (e.g., `nflow skip` on an impl task auto-skips its verify), it looks for the next task in `sort_order` with `kind='verify'` under the same parent story.

**Acceptance criteria** are present on all work item types:
- Epic: high-level criteria for the entire feature
- Story: criteria for the user-facing scenario
- Task (impl): specific criteria for what the task must achieve
- Task (verify): inherited from the impl task, used as the checklist to verify

### dependencies

DAG edges between work items. `blocker_id` must complete before `blocked_id` can start.

```sql
CREATE TABLE dependencies (
    blocker_id  TEXT NOT NULL REFERENCES work_items(id) ON DELETE CASCADE,
    blocked_id  TEXT NOT NULL REFERENCES work_items(id) ON DELETE CASCADE,
    PRIMARY KEY (blocker_id, blocked_id)
);

CREATE INDEX idx_deps_blocker ON dependencies(blocker_id);
CREATE INDEX idx_deps_blocked ON dependencies(blocked_id);
```

Dependencies operate at the **story** level. A story is `ready` when all its blocker stories are `done`.

### agent_runs

Log of every agent execution attempt.

```sql
CREATE TABLE agent_runs (
    id              TEXT PRIMARY KEY,      -- UUID
    work_item_id    TEXT NOT NULL REFERENCES work_items(id) ON DELETE CASCADE,
    claude_session_id TEXT NOT NULL,       -- claude session ID
    pid             INTEGER,               -- OS process ID of claude process
    pid_start_time  INTEGER,               -- process start time (clock ticks from /proc/{pid}/stat), for PID reuse detection
    status          TEXT NOT NULL,
    -- Statuses: running, completed, failed, cancelled
    started_at      TEXT NOT NULL,
    finished_at     TEXT,
    exit_code       INTEGER,
    log_path        TEXT,                  -- path to output log file
    error_message   TEXT,                  -- error details if failed
    created_at      TEXT NOT NULL
);

CREATE INDEX idx_agent_runs_work_item ON agent_runs(work_item_id);
CREATE INDEX idx_agent_runs_status ON agent_runs(status);
```

### decomposition_sessions

Tracks decomposition attempts (plan generation from specs).

```sql
CREATE TABLE decomposition_sessions (
    id              TEXT PRIMARY KEY,      -- UUID
    project_id      TEXT NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    wave_number     INTEGER NOT NULL,      -- auto-increment per project (1, 2, 3, ...)
    claude_session_id TEXT,               -- for resuming feedback loop
    status          TEXT NOT NULL DEFAULT 'in_progress',
    -- Statuses: in_progress, approved, discarded
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

CREATE UNIQUE INDEX idx_decomp_project_wave ON decomposition_sessions(project_id, wave_number);

-- Which specs were used in this decomposition
CREATE TABLE decomposition_specs (
    session_id  TEXT NOT NULL REFERENCES decomposition_sessions(id) ON DELETE CASCADE,
    spec_id     TEXT NOT NULL REFERENCES specs(id) ON DELETE CASCADE,
    PRIMARY KEY (session_id, spec_id)
);
```

## Status State Machines

### Spec Status

```
draft ──────► approved ──────► decomposed
  ▲               │
  │  (reopen)     │
  └───────────────┘

Any state ──────► deleted    (via nflow spec delete)
```

- `draft → approved`: user approves the spec
- `approved → draft`: user reopens for editing
- `approved → decomposed`: plan generated from this spec
- `decomposed → approved`: via `nflow plan discard` on the spec's wave (then can be reopened to `draft`)
- `* → deleted`: user deletes the spec. If `decomposed`, must discard its wave's plan first.

### Epic Status

Epic status is **materialized** — stored in the `status` field and updated by the daemon whenever a child story's status changes. The daemon recalculates the epic status using these rules:

| Condition | Status |
|-----------|--------|
| All stories `pending` | `pending` |
| Any story `in_progress` or `ready` | `in_progress` |
| All stories `done` | `done` |
| Any story `failed` (and none `in_progress`) | `failed` |
| At least one story `done`, rest `done` or `cancelled` | `done` |
| All stories `cancelled` | `cancelled` |

The daemon updates epic status as part of the `propagate_status_changes()` step in the scheduler loop. After any story status change (including from client commands like `retry`, `skip`, `continue`), the parent epic's status is recalculated and written to the database. This avoids JOIN-based computation on every read and keeps the status field consistent for all consumers (CLI, TUI, direct DB queries).

### Story Status

```
pending ──────► ready ──────► in_progress ──────► done
                  │                 │
                  │                 ├──────────► failed ────► in_progress (retry/continue)
                  │                 │
                  │                 └──────────► cancelled
                  │                                  │
                  │                                  └──► in_progress (nflow continue)
                  │
                  └──────────────────────────► cancelled
                                                   │
                                                   └──► in_progress (nflow continue)
```

- `pending → ready`: all blocker stories are `done`
- `ready → in_progress`: scheduler picks up the story, creates worktree
- `in_progress → done`: all tasks in story are `done`, MR created
- `in_progress → failed`: a task failed and user needs to intervene
- `failed → in_progress`: via `nflow retry` or `nflow continue`
- `in_progress → cancelled`: user stops the story via `nflow stop`
- `ready → cancelled`: user cancels before execution via `nflow cancel`
- `pending → cancelled`: user cancels before execution via `nflow cancel`
- `cancelled → in_progress`: via `nflow continue` when worktree exists (resets cancelled tasks to pending)
- `cancelled → ready`: via `nflow continue` when no worktree and all dependencies met
- `cancelled → pending`: via `nflow continue` when no worktree and dependencies unmet

**Cancelled stories and dependencies:** Cancelled stories do not block dependent stories. Dependencies treat `cancelled` the same as `done` for unblocking purposes (the user explicitly decided to skip it). **Warning:** When cancelling a story that has dependents, nflow displays a warning: `"Story {id} has {n} dependent stories that may fail without it. Continue? [y/N]"`. Use `--force` to skip.

### Task Status

```
pending ──────► in_progress ──────► done
                      │
                      ├──────────► failed ────► in_progress (nflow retry)
                      │                    └──► done        (nflow skip)
                      │
                      └──────────► cancelled ──► pending    (nflow continue on story)
```

- `pending → in_progress`: previous task in story is `done` (sequential within story)
- `in_progress → done`: agent completed, commit created (impl tasks) or verification passed (verify tasks)
- `in_progress → failed`: agent failed, escalated to user
- `failed → in_progress`: via `nflow retry` (new agent_run)
- `failed → done`: via `nflow skip` (marked with `skipped=true` metadata)
- `in_progress → cancelled`: parent story was stopped by user
- `pending → cancelled`: parent story was cancelled (remaining tasks auto-cancelled)
- `cancelled → pending`: when parent story is resumed via `nflow continue`

## Entity Relationships

```
project 1──────* spec
project 1──────* decomposition_session (wave)

decomposition_session 1──────* work_item (epic, story, task)
decomposition_session *──────* spec (via decomposition_specs)

epic    1──────* work_item (story)
story   1──────* work_item (task)

story   *──────* story (via dependencies table, within same wave)

work_item 1────* agent_run
```

## Short ID Mapping

During decomposition, Claude generates short IDs (E1, S1, T1). These are used only during the decomposition session for `depends_on` references. When nflow stores work items in SQLite:

1. Each work item gets a UUID (`id` field)
2. The short ID is stored in a `short_id` column (added for display purposes)
3. `depends_on` references (e.g., `"S1"`) are resolved to UUIDs during insertion
4. Short IDs are scoped to a decomposition session (wave) — they are not globally unique
5. Since each wave is a separate decomposition session, short IDs like S1, T1 may repeat across waves. Display and CLI format includes the wave prefix for disambiguation: `W1-S1`, `W2-T3`, `W1-T2v`
6. On re-generation (feedback), all work items from the session are deleted and recreated with new UUIDs

Short IDs serve two purposes:
1. **Display** in CLI/TUI (e.g., `W1-S1: User Login`, `W2-T3v: Verify password hashing`)
2. **CLI input** — all commands that accept `<task-id>` or `<story-id>` use wave-prefixed short IDs. nflow resolves them to UUIDs internally (e.g., `nflow retry W1-T3v`, `nflow continue W2-S2`)

Internal references always use UUIDs. The wave prefix + short ID combination is unique within a project.

## Concurrency

- SQLite WAL mode is enabled for concurrent reads from multiple clients
- The daemon is the **sole writer** to the database. CLI/TUI clients never write directly.
- All state mutations go through daemon commands via the Unix socket
- This eliminates write contention: the daemon processes commands sequentially on its main loop
- If two TUI clients send conflicting commands (e.g., both give plan feedback), the daemon processes them in order — second feedback operates on the result of the first
- Optimistic locking is not needed because the daemon serializes all writes

Multiple waves can execute concurrently. The daemon treats stories from all approved waves equally when scheduling — `max_parallel` is a global limit shared across all waves.

## Migrations

Migrations use a simple numbered file scheme:

```
migrations/
├── 001_init.sql
├── 002_add_short_id.sql
└── ...
```

Mechanism:
1. A `schema_version` table tracks the current version
2. On daemon start, nflow scans the `migrations/` directory
3. If there are pending migrations, nflow creates a backup: `cp nflow.db nflow.db.bak-v{current_version}` (before any migration runs). Only one backup per version is kept — subsequent runs overwrite the same backup file.
4. Applies all migrations with a number > current version, in order
5. Each migration runs in a transaction
6. Migration files are embedded in the binary at compile time via `include_str!`

No external migration tool (refinery, etc.) is used — the mechanism is built into nflow-core (~50 lines of code).

```sql
CREATE TABLE IF NOT EXISTS schema_version (
    version INTEGER NOT NULL,
    applied_at TEXT NOT NULL
);
```

## Notes

- All IDs are UUID v4 strings
- All timestamps are ISO 8601 in UTC
- Migrations are applied on daemon start
